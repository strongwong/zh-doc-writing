# 去 AI 味清单

AI 生成的中文有一套可识别的习惯。单看每一处都不算错，叠在一起就是“一股 AI 味”：读者会觉得作者没真正做过这件事，只是在填模板。

自检时按下面 A～E 五类逐类过全文。每类先读“为什么”，再对照例子。改的方向永远是同一个：**换成具体事实，或者删掉**。

## 目录

- A. 词语：套话、宣传词、黑话、翻译腔
- B. 句式：对比、递进、设问、对称
- C. 段落与篇章：开头、结尾、小结、凑数
- D. 格式：加粗、列表、标题、符号
- E. 内容：空洞、含糊、伪精确、自我指涉
- 改写示例
- 不要矫枉过正

## A. 词语

**为什么**：这些词信息量接近零，但读起来很“满”。一段话里去掉它们意思不变，就说明它们只是填充。

| 类别 | 例子 | 改法 |
|---|---|---|
| 拔高词 | 至关重要、不可或缺、举足轻重、重要意义、核心价值、关键作用 | 写出不这样做的具体后果；写不出就删 |
| 宣传词 | 强大、灵活、无缝、全面、极致、优雅、卓越、高效、轻松、一站式、开箱即用 | 换成数字或事实：“支持 3 种启动介质”，“单次调用 < 1 ms” |
| 黑话 | 赋能、助力、抓手、闭环、沉淀、对齐、颗粒度、打通、底层逻辑、范式、生态、心智 | 换白话。代码或业务里的正式名称（“调用链路”）保留 |
| 书面虚词 | 旨在、致力于、彰显、凸显、深入、充分、有效、显著、切实 | “旨在提高” → “为了提高”；“有效降低” → “降低了 30%” |
| 翻译腔 | 进行 + 动词、对……进行……、通过……的方式、作为一个……、基于……、针对……、使得 | 直接用动词：“对数据进行校验” → “校验数据” |
| 连接词堆砌 | 此外、同时、另外、与此同时、进一步地、从而、进而、因此（每段开头都有） | 删掉大部分，前后句的逻辑读者自己看得出 |
| 引号强调 | 所谓的“优化”、这种“智能” | 去掉引号；真有讽刺意味就直接说问题 |
| 比喻 | 就像……一样、可以把它想象成……、如同一座桥梁 | 技术文档里基本不用。确实难懂时给一个真实例子，不给比喻 |
| 拟人 | 函数会聪明地判断、系统会贴心地提示 | 写它实际做了什么：“函数检查返回值” |

## B. 句式

**为什么**：AI 喜欢修辞结构，因为结构本身显得“有思考”。技术文档要的是信息，结构越花哨，读者越要费力拆开。

| 句式 | 例子 | 改法 |
|---|---|---|
| 否定对比 | 这不是一个简单的 bug，而是一个设计缺陷 | 直接说：“这是设计缺陷：……” |
| 递进 | 不仅提高了性能，更提升了可维护性 | 拆成两句陈述，各带事实 |
| 设问自答 | 为什么会这样？原因很简单：…… / 关键在于什么？ | 直接给结论 |
| 让步转折 | 虽然……但是……（每段都有） | 只在真有取舍时用 |
| 一方面另一方面 | 一方面……另一方面…… | 两件事分开写，或用列表 |
| 排比三连 | 更快、更稳、更安全 | 只留有事实支撑的那个 |
| 同义重复 | 简单来说 / 换句话说 / 也就是说，后面把前句再说一遍 | 删掉前句或后句，留更清楚的那个 |
| 冒号引子 | 答案是：/ 结论是：/ 核心思路是： | 删掉引子，直接写答案 |
| 万能句尾 | ……，从而确保系统的稳定性和可靠性 | 删掉“从而确保”分句，或写出具体保证了什么 |

## C. 段落与篇章

**为什么**：AI 按“总—分—总”模板组织全文，开头铺垫、结尾复述、每段末尾再小结一次。人写文档时，写完就停。

- **开头铺垫**：“随着……的快速发展”“在当今……时代”“众所周知”“本文将从以下几个方面介绍”。删掉，第一句直接说要解决的问题或结论。
- **结尾复述**：“综上所述”“总的来说”“总而言之”“通过以上分析可以看出”。删掉。需要结尾时只写新信息：下一步、待定问题、负责人。
- **段末小结**：每段最后一句把本段再说一遍。删掉。
- **客套**：“希望对你有帮助”“如有问题欢迎交流”“祝你使用愉快”。删掉。
- **凑三项**：每个列表都正好三条，每条都一样长。有几项写几项，长短随内容。
- **对称段落**：每节都是“定义—优点—缺点—总结”四段，每段长度相近。按内容需要写，有的节一句话就够。
- **主动附加**：用户没问，却在末尾加“最佳实践建议”“注意事项”“扩展阅读”。删掉，除非真有读者必须知道的风险。

## D. 格式

**为什么**：过度格式化让页面看起来“有条理”，实际打断阅读。读者分不出哪个加粗真的重要。

- 每条列表都是 `**标签**：解释`。只在参数表、术语表这类真正的键值结构里用；其他改成普通列表或段落。
- 一段话里多处加粗。一屏最多一两处，只给警告和关键词。
- 一两句话也拆成列表；小标题比段落还密。合并成段落，去掉只管一两句话的标题。
- emoji 当标题或列表符号（✅ 🚀 💡）。删掉。
- 感叹号。改句号。
- 破折号 `——` 用来插入解释。改逗号、括号、冒号，或拆句。全文最多一两处。
- 表格只有两列、每行一句话。改成列表或段落。

## E. 内容

**为什么**：这是最难改、也最伤信任的一类。形式上的 AI 味删掉就好，内容空洞得回去补事实。

- **空洞结论**：“该方案具有良好的扩展性”。问自己：扩展到什么？怎么验证的？写出来，写不出就删。
- **模糊归因**：“业界普遍认为”“有研究表明”“很多开发者反馈”。给出处，或者改成自己的判断并说明依据。
- **过度含糊**：“在某种程度上”“在一定情况下可能会”“通常来说”。确定就直接说；不确定就写清条件和验证方法。
- **过度自信**：没有验证过的事写成“确保”“彻底解决”“完全避免”。改成实际验证到的范围。
- **伪精确**：没有测量过的数字（“性能提升约 40%”）。没测就不写数字，或者注明“估计”和估算方法。
- **自我指涉**：“本文将”“下面我们来看”“接下来介绍”“如上所述”。删掉，直接写内容。
- **面面俱到**：列出所有可能情况，但不说哪个最可能、先做哪个。给出推荐和理由。

## 改写示例

**例 1：开头**

> 差：随着软件行业的快速发展，代码质量变得越来越重要。在这样的背景下，自动化测试作为研发流程的关键环节，其作用至关重要。本文将从以下几个方面对自动化测试的覆盖策略进行深入分析。
>
> 好：每次合并请求都会自动运行测试，10 分钟内出结果。本文说明测试覆盖的范围，以及失败后的处理方式。

**例 2：结论**

> 差：通过引入重试机制，不仅有效提升了系统的鲁棒性，更为后续的功能扩展奠定了坚实的基础。
>
> 好：加入 3 次重试后，注入 1% 读错误时启动成功率从 92% 升到 100%（1,000 次测试）。

**例 3：列表**

> 差：
> - **高性能**：采用先进的算法，显著提升处理速度。
> - **高可靠**：多重校验机制，全面保障数据安全。
> - **易扩展**：模块化设计，轻松应对未来需求。
>
> 好：镜像校验用 SHA-256 + ECDSA P-256，单次耗时 18 ms。校验失败时切换到备份镜像，两份都失败则停在安全状态并上报错误码。

**例 4：否定对比与设问**

> 差：问题的根源是什么？这不是一个简单的时序问题，而是状态机设计上的缺陷。
>
> 好：根因在状态机：`BOOT_RETRY` 状态没有清除上一次的错误码。

## 不要矫枉过正

- 清单里的词不是禁用词。“关键路径”“核心板”“生态”是正式术语时照用。判断标准是：删掉或换成事实后，意思是否变得更清楚。
- 不要为了“去 AI 味”故意写错字、加口头禅、写得不规范。目标是像工程师，不是像随手聊天。
- 不要把所有列表都改成段落。真正并列、需要扫读的内容（步骤、参数、检查项）就该用列表。
- 原文作者的个人风格（比如偏爱某些连接词）如果不影响清晰度，不必改。
